# Atoms 前端体验审视

审视日期：2026-09-12  
范围：桌面端已登录/未登录首页、登录、项目空状态、模型设置；项目工作区补充代码层检查。

## 总评

当前页面的基础方向是对的：配色克制、信息不嘈杂、主色一致，也已经有明确的页面路由和核心任务。显得粗糙的根因不是颜色，而是内容层级过少、页面密度偏低、主操作与其上下文分离，导致大量区域像“空白画布 + 一组控件”。

建议保留现有灰白底和紫色主色，优先重构布局节奏与组件层级，再做阴影、圆角等微调。

## 逐页检查

### 1. 未登录首页 — 健康度：一般

![未登录首页](/Users/shenzhijian/code/my-project/atoms/.audit/frontend-2026-09-12/01-home-logged-out.png)

优点：价值主张清楚，首屏没有干扰信息，登录入口明确。

问题：正文区偏左上但按钮悬在右侧，视觉重心不稳定；大片空白没有承载产品能力或信任信息；侧栏在未登录状态仍占据较强注意力。页面更像登录前占位页，尚未形成完整的产品入口。

建议：把标题、说明和 CTA 组织为一个更紧凑的 hero；在不扩大功能范围的前提下，用三条简短能力说明补齐首屏，例如“对话生成 / 隔离运行 / 实时预览”。

### 2. 登录页 — 健康度：较好，但偏通用

![登录页](/Users/shenzhijian/code/my-project/atoms/.audit/frontend-2026-09-12/05-login.png)

优点：表单层级清楚，标签与输入框对应，主按钮足够突出。

问题：卡片与全局导航缺少关系，四周空白过多；注册切换入口视觉过弱；错误信息没有 `role="alert"` 或 `aria-live`；缺少统一的按钮键盘焦点样式。

建议：缩短卡片上方距离，弱化此页侧栏导航或给主区域增加简短产品说明；补齐焦点态和错误播报。

### 3. 已登录首页 / 创建入口 — 健康度：一般

![已登录首页](/Users/shenzhijian/code/my-project/atoms/.audit/frontend-2026-09-12/02-home-logged-in.png)

优点：单一主任务很明确，用户进入后知道应该描述应用。

问题：输入框、创建按钮、配置提示是三个松散元素，按钮通过 `float` 靠右放置，像后补上去的；大标题尺寸和周围留白都偏大；配置模型是创建前提，但提示权重很低，容易到提交时才发现。

建议：改为完整的“对话输入器”卡片：输入区 + 底部工具/状态行 + 右侧主按钮。未配置模型时在输入器顶部展示轻量状态条，并让设置入口更明确。避免使用 `float` 控制关键布局。

### 4. 项目列表空状态 — 健康度：较差

![项目空状态](/Users/shenzhijian/code/my-project/atoms/.audit/frontend-2026-09-12/04-projects-empty.png)

优点：空状态文案容易理解。

问题：文案告诉用户“从首页开始”，但没有按钮，形成任务断点；巨大的空卡片只有两行文字，进一步放大了粗糙感；页面标题和空状态之间缺少承接。

建议：空状态内直接提供“创建第一个项目”主按钮，跳转到首页输入区；缩小空卡片高度，并增加一个真实图标库中的简单图标或步骤提示。这个是最高优先级的体验修复。

### 5. 模型设置 — 健康度：一般

![模型设置](/Users/shenzhijian/code/my-project/atoms/.audit/frontend-2026-09-12/03-settings.png)

优点：字段数量少，保存和测试连接的任务清晰。

问题：表单直接铺在空白页面上，缺少设置组和配置状态；`Base URL`、`API Key` 与中文界面混用；“测试连接”和“保存”的关系不够明确；反馈文本没有稳定的状态区域，成功/失败时页面会轻微跳动。

建议：把配置放入一个窄卡片或分组面板；页头增加“已配置 / 未配置”状态；统一字段语言并提供简短帮助文本；在按钮上方预留固定反馈区域。

### 6. 项目工作区 — 健康度：未完成视觉验证

当前账户没有项目，为避免写入用户数据，没有为了审视而创建测试项目，因此本轮没有工作区截图。

代码层可见的主要风险：左侧对话、运行进度和输入区都挤在同一卡片内，缺少空会话引导；运行输出只是连续段落，事件类型和层级不明显；只在 `700px` 处理全局侧栏，没有为双栏工作区定义响应式降级，窄屏可能被压缩；预览地址框移除了焦点视觉反馈，即使只读也会造成键盘状态不明确。

建议：工作区单独作为下一轮视觉验收重点，至少覆盖空会话、运行中、成功、失败和预览不可用五种状态。

## 跨页面高优先级优化

1. **建立统一页面骨架。** 内页标题建议控制在 36–44px；统一标题区、内容区、卡片区的垂直节奏，减少“巨大标题 + 大片空白”。
2. **把主操作和上下文收进同一组件。** 首页输入、设置反馈、项目空状态都需要完整的任务组件，而不是零散控件。
3. **重做侧栏的精细度。** 保留 240px 宽度即可；为导航加入统一线性图标，激活态用色块或左侧标记，降低全局按钮阴影；账户区做成紧凑菜单。导航应使用真实链接，而不是只用按钮模拟跳转。
4. **统一表面与阴影。** 现在主按钮阴影比其他组件强很多。建议只保留两级 elevation：默认无阴影，浮层/重要卡片使用一档柔和阴影。
5. **补齐状态设计。** 为加载、空、成功、失败、未配置状态设置稳定位置和一致组件，避免只出现一行文字。
6. **修复移动端导航。** 当前小屏将品牌、三项导航和账户全部放入同一行，空间不足。应改为顶部栏 + 可展开导航，工作区双栏在窄屏切换为“对话 / 预览”标签。

## 可访问性风险

- 浅灰提示文字 `#a1a1aa` 在浅灰背景上对比度偏低，尤其是首页说明和占位文本。
- 通用按钮没有显式的 `:focus-visible` 样式，键盘用户难以判断当前位置。
- 登录、项目和设置的错误/成功反馈缺少 `role="alert"` 或 `aria-live`。
- 侧栏页面跳转使用 `<button>`，无法获得链接的复制地址、在新标签页打开等原生行为。
- 本轮只验证了桌面宽度；移动端和键盘完整走查仍需单独验证。

## 推荐实施顺序

第一轮只做结构收口：首页对话输入器、项目空状态 CTA、设置卡片与状态、侧栏导航精简、工作区窄屏降级。  
第二轮再做视觉统一：字号、间距、圆角、阴影、图标和微交互。  
第三轮做可访问性与状态验收：键盘、对比度、错误播报、加载/失败/空状态。
